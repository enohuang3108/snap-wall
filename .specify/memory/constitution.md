# Snap Wall 專案憲章

## 核心原則

### I. 代碼品質至上（不可協商）

每一行代碼都必須達到生產級別的品質標準：

- **可讀性優先**：代碼應該自我解釋，變數和函式命名必須清晰明確
- **單一職責**：每個函式、類別或模組只負責一件事情
- **避免過早優化**：優先選擇簡單、直接的解決方案，除非有明確的效能需求
- **一致性**：遵循專案既有的編碼風格和模式
- **無警告政策**：代碼必須通過所有 linter 和 formatter 檢查，零警告才能提交

**理由**：高品質的代碼是長期可維護性的基礎。技術債務會隨時間累積，導致開發速度下降和 bug 增加。

### II. 測試驅動開發（強制執行）

測試不是可選項，而是開發流程的核心部分：

- **測試優先**：在實作功能之前必須先撰寫測試
- **紅-綠-重構**：測試失敗 → 實作 → 測試通過 → 重構
- **測試覆蓋率**：核心業務邏輯必須達到 80% 以上的測試覆蓋率
- **獨立可測試**：每個功能必須可以獨立測試，不依賴其他功能
- **測試類型分層**：
  - 單元測試：測試個別函式和類別
  - 整合測試：測試模組間的互動
  - 契約測試：測試 API 端點和外部介面

**理由**：測試是代碼品質的保證。沒有測試的代碼無法安全地重構或擴展。

### III. 使用者體驗一致性

所有使用者介面和互動必須保持一致的體驗：

- **設計系統**：使用統一的設計語言和元件庫
- **無障礙優先**：遵循 WCAG 2.1 AA 級標準
- **回饋即時**：所有使用者操作必須有明確的視覺或聽覺回饋
- **錯誤處理友善**：錯誤訊息必須清晰、可操作，提供解決方案
- **響應式設計**：介面必須在不同裝置和螢幕尺寸上正常運作
- **載入狀態**：任何超過 200ms 的操作都必須顯示載入狀態

**理由**：一致的使用者體驗建立信任感，減少學習曲線，提升使用者滿意度。

### IV. 效能標準（可測量）

效能要求必須明確定義且可測量：

- **響應時間**：
  - API 端點：95th percentile < 200ms
  - 頁面載入：First Contentful Paint < 1.5s
  - 互動響應：< 100ms
- **資源使用**：
  - 記憶體佔用：< 100MB (瀏覽器環境)
  - Bundle 大小：初始載入 < 200KB (gzipped)
- **擴展性**：
  - 支援 1,000 個並發使用者
  - 資料庫查詢必須有適當的索引
- **監控**：所有關鍵效能指標必須被監控和記錄

**理由**：效能直接影響使用者體驗和系統成本。明確的標準確保效能不會隨時間退化。

### V. 安全第一

安全性是所有功能的基本要求，不是事後添加的功能：

- **輸入驗證**：所有外部輸入必須經過嚴格驗證和淨化
- **防範常見攻擊**：
  - XSS (Cross-Site Scripting)
  - SQL Injection
  - CSRF (Cross-Site Request Forgery)
  - Clickjacking
- **敏感資料保護**：
  - 密碼必須使用 bcrypt 或 Argon2 加密
  - 敏感資料傳輸必須使用 HTTPS
  - API 金鑰和密鑰不得硬編碼
- **權限控制**：實施最小權限原則
- **依賴項安全**：定期掃描和更新依賴項的安全漏洞

**理由**：安全漏洞可能導致資料外洩、財務損失和信譽損害。預防永遠比補救更有效。

## 品質門檻

所有代碼在合併到主分支前必須通過以下檢查：

### 必要檢查項目

- [ ] 所有測試通過（單元、整合、契約）
- [ ] 測試覆蓋率達標（核心邏輯 ≥ 80%）
- [ ] Linter 和 Formatter 零警告
- [ ] 效能基準測試通過
- [ ] 安全掃描通過
- [ ] Code Review 通過（至少一位審核者批准）
- [ ] 無未解決的 TODO 或 FIXME（除非有對應的 issue 編號）

### Code Review 準則

審核者必須檢查：

1. **正確性**：代碼是否實作了所需的功能？
2. **測試**：測試是否充分且有意義？
3. **可讀性**：代碼是否容易理解？
4. **效能**：是否有明顯的效能問題？
5. **安全性**：是否有潛在的安全漏洞？
6. **一致性**：是否遵循專案慣例？

## 效能標準詳細說明

### 前端效能

- **Core Web Vitals**：
  - LCP (Largest Contentful Paint) < 2.5s
  - FID (First Input Delay) < 100ms
  - CLS (Cumulative Layout Shift) < 0.1
- **資源優化**：
  - 圖片使用 WebP 格式並進行壓縮
  - 實施程式碼分割（Code Splitting）
  - 使用 lazy loading 延遲載入非關鍵資源
- **快取策略**：
  - 靜態資源必須設定適當的快取標頭
  - 實施 Service Worker 進行離線支援（如適用）

### 後端效能

- **資料庫**：
  - 所有查詢必須在 50ms 內完成（95th percentile）
  - 使用 EXPLAIN 分析並優化慢查詢
  - 實施適當的索引策略
- **API 設計**：
  - 實施分頁避免大量資料傳輸
  - 使用 GraphQL 或欄位選擇避免過度獲取
  - 實施適當的快取層（Redis, CDN）
- **並發處理**：
  - 使用連接池管理資料庫連接
  - 實施請求限流防止濫用

## 治理規則

### 憲章優先權

本憲章的原則優先於所有其他開發慣例和指南。如有衝突，以本憲章為準。

### 修訂程序

1. **提案**：任何團隊成員都可以提出修訂提案
2. **討論**：提案必須經過團隊討論和評估
3. **批准**：修訂需要至少 2/3 團隊成員同意
4. **文件化**：所有修訂必須記錄原因和影響範圍
5. **遷移計畫**：如果修訂影響現有代碼，必須提供遷移計畫

### 版本控制規則

憲章版本遵循語義化版本控制：

- **MAJOR**：向後不相容的原則移除或重新定義
- **MINOR**：新增原則或大幅擴展指南
- **PATCH**：澄清、措辭調整、修正錯字

### 合規性審查

- 每個 Pull Request 必須驗證是否符合憲章原則
- 如需違反原則，必須提供充分的理由並記錄在案
- 複雜度必須有正當理由（參見 plan-template.md 的 Complexity Tracking）

### 開發指南

團隊成員應參考個人的 `~/.claude/CLAUDE.md` 檔案以獲得運行時的開發指導。該檔案提供具體的實踐方法和決策框架，與本憲章互補。
